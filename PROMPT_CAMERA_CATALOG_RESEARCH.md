# Промпт: проверка прайса и создание JSON-каталога IP-камер

Скопируйте текст промпта ниже в агента и приложите полный прайс и, если есть, локальный HTML-кэш карточек поставщика.

---

Ты — агент по исследованию характеристик IP-камер для проекта калькулятора подбора камер.

## Цель

Я передам тебе полный прайс. Нужно:

1. Найти в прайсе все позиции, которые являются IP-камерами.
2. Для каждой IP-камеры собрать необходимые характеристики.
3. Создать новый JSON-каталог с нуля по структуре объекта из этого промпта.
4. Включить в JSON все IP-камеры из переданного прайса и не добавлять позиции, которых в прайсе нет.
5. Подготовить итоговый JSON, который можно сразу использовать в проекте.
6. Проверить каждую позицию прайса: не оставлять строку без результата проверки.

Работай до завершения всего списка. Не останавливайся после выборки примеров или части моделей.
Не возвращай только план, предварительный отчёт, классификацию кандидатов или JSON с одним-двумя проверенными примерами. Это не завершение задачи. Продолжай исследование пакетами до выполнения критериев приёмки в конце промпта. Не проси пользователя подтвердить продолжение.

## Входные данные

Я предоставлю:

- полный прайс XLSX/CSV либо ссылку на него;
- при наличии — локальный HTML-кэш карточек поставщика.

Используй структуру JSON-объекта из раздела «Пример JSON-объекта». Не переименовывай поля и не меняй типы значений. Создай новый JSON только по строкам переданного прайса, классифицированным как IP-камеры. Не добавляй позиции из других файлов или источников.

## Шаг 1. Разобрать прайс

Для каждой строки категории «Камеры»:

- сохрани код поставщика/артикул, бренд, модель, цену и URL карточки, если они есть;
- определи, является ли позиция IP-камерой, аналоговой камерой, аксессуаром или неопределённой позицией;
- не считай устройство IP-камерой только по слову «камера»;
- используй модель, бренд, код, описание и карточку товара;
- создай полный реестр всех строк прайса с решением по каждой позиции.

Если тип позиции определить не удалось, не пропускай её молча: помести её в отдельный список «требует проверки» с причиной.

Отсутствие URL в прайсе не является основанием остановить исследование или пометить IP-камеру как неразобранную. Используй точные бренд, модель и код для поиска в интернете. Если модель имеет несколько вариантов написания, ищи по каждому варианту и проверяй найденную модификацию по коду и характеристикам.

## Шаг 2. Проверить модели и модификации в самом прайсе

Определи модель и модификацию для каждой IP-камеры, используя:

- бренд и модель;
- код поставщика/артикул;
- объектив и суффиксы модификации;
- карточку товара и документацию производителя.

Не объединяй разные модификации только потому, что у них похожие названия. Учитывай объектив, цвет корпуса, тип подсветки, Wi-Fi/PoE, ревизию, региональный суффикс и другие отличия, если они влияют на характеристики. Дедуплицируй только подтверждённые повторы внутри переданного прайса. Если у одной модели несколько кодов или цен, не теряй ни одну строку: оставь отдельные позиции либо отрази несколько кодов по схеме из примера и объясни решение в отчёте.

Для каждой строки прайса укажи статус:

- IP-камера, включена в JSON;
- не IP-камера;
- не удалось однозначно определить тип или модель.

## Шаг 3. Найти характеристики

Для каждой IP-камеры найди и проверь все характеристики ниже. Не прекращай поиск после нахождения разрешения или объектива: пройди весь список полей.

Обработай каждую позицию IP-камеры отдельно. Для каждой выполни поиск по точной модели и бренду, затем найди официальный сайт производителя, карточку модели или официальный даташит. Если первая попытка ничего не дала, используй альтернативные написания модели, код производителя и название серии. Не переноси значения с соседней модели только на основании похожего имени.

Веди рабочий реестр исследования с одной строкой на каждую позицию прайса: код, бренд и модель, результат классификации, запросы/варианты поиска, найденные источники, поля которые подтверждены, поля которые остались неизвестными и причина. Этот реестр нужен для контроля полного охвата; не заменяй его выборочными примерами.

### Обязательные для геометрического подбора

- горизонтальное разрешение в пикселях;
- диапазон фокусного расстояния: минимум и максимум;
- оптический формат сенсора.

Для многоканальной или многосенсорной камеры укажи эти поля отдельно для каждого канала в `channels[]`. Не смешивай разрешение одного канала с форматом сенсора или фокусным расстоянием другого. Если у камеры заполнен `channels[]`, калькулятор рассчитывает каждый канал отдельно и не использует общие геометрические поля `specs` вместо данных канала.

Сохраняй `sensor_format` строкой максимально близко к источнику. Для геометрического расчёта калькулятор использует справочное соответствие оптического формата. Он распознаёт основные форматы `1/4`, `1/3.2`, `1/3`, `1/2.9`, `1/2.8`, `1/2.7`, `1/2.5`, `1/1.8` и `1/1.2` дюйма; кавычки и пробелы нормализуются. Для одного сшитого панорамного канала, сформированного несколькими сенсорами, сохрани множитель `×N` в значении формата и поясни это в `note`: калькулятор учитывает множитель в геометрии такого канала. Если формат другой, всё равно укажи подтверждённое исходное значение и отметь, что для расчёта потребуется добавить его в справочник форматов.

### Дополнительные характеристики сенсора и камеры

- мегапиксели камеры;
- тип сенсора, например CMOS, если он опубликован;
- разрешение сенсора в мегапикселях, если оно отдельно указано;
- горизонтальный, вертикальный и диагональный углы обзора;
- минимальная освещённость в люксах с указанием режима/условий;
- наличие ИК-подсветки и её дальность;
- наличие белой LED-подсветки и её дальность;
- рейтинг IP и IK;
- поддержка WDR и значение в дБ;
- PoE;
- Wi-Fi;
- наличие встроенного микрофона;
- наличие встроенного динамика;
- PTZ;
- максимальная частота кадров;
- максимальный размер карты microSD;
- аналитика человека, автомобиля и события, если поля предусмотрены текущей схемой;
- форм-фактор камеры: цилиндрический, купольный, турельный, поворотный и т. п.;
- цена, валюта и код поставщика из актуального прайса.

Проверь точное наличие встроенного микрофона отдельно от аудиовхода/аудиовыхода. Наличие аудиопортов или поддержки аудиокодеков не доказывает наличие встроенного микрофона. Учитывай формулировки вроде «Built-in Mic: Yes», «микрофон — есть», «встроенные микрофоны — 2». Сохраняй источник этого подтверждения.

## Источники и достоверность

Используй источники в таком порядке:

1. официальный сайт производителя и официальные даташиты;
2. официальный сайт дистрибьютора;
3. карточка поставщика из прайса;
4. другие надёжные источники — только если официальные данные недоступны.

Для каждого заполненного или исправленного значения сохрани URL источника. Если источник производителя и карточка продавца расходятся, укажи расхождение; не выбирай значение молча.

Для каждого заполненного поля должен быть источник, который подтверждает именно это значение. Сохраняй прямые URL страниц и даташитов, а не только домен или страницу поиска. В реестре укажи отдельно, какие поля подтверждает каждый источник.

Не выдумывай значения:

- не выводи точное разрешение в пикселях из одного только числа мегапикселей;
- не считай фокусное расстояние из угла обзора без необходимых подтверждённых параметров;
- не подставляй характеристики соседней модели без доказательства, что это та же модификация;

Значение `null` используй, когда характеристику не удалось подтвердить. Не подменяй `null` значениями `false`, `0` или предположением.

## Камеры с несколькими каналами или объективами

Для двухканальных, панорамно-PTZ, многосенсорных и многолинзовых камер не смешивай параметры разных каналов в одной записи.

Для таких камер добавляй на уровне записи поле `channels` — массив каналов. Каждый элемент должен содержать название канала, его собственные геометрические параметры и источник:

```json
{
  "channels": [
    {
      "channel": "Панорамный канал",
      "resolution_width_px": 4096,
      "resolution_height_px": 1860,
      "sensor_format": "1/2.7\" × 2",
      "focal_length_min_mm": 2.8,
      "focal_length_max_mm": 2.8,
      "source": "https://manufacturer.example/datasheet.pdf",
      "note": "Разрешение относится к объединённому панорамному потоку двух сенсоров."
    },
    {
      "channel": "PTZ-канал",
      "resolution_width_px": 2688,
      "resolution_height_px": 1520,
      "sensor_format": "1/2.8\"",
      "focal_length_min_mm": 5.6,
      "focal_length_max_mm": 140,
      "source": "https://manufacturer.example/datasheet.pdf",
      "note": null
    }
  ]
}
```

В `channels[]` обязательно укажи для каждого канала `resolution_width_px`, `sensor_format`, `focal_length_min_mm` и `focal_length_max_mm`; `resolution_height_px`, `source` и `note` также сохраняй, если они опубликованы. Если какое-либо значение не подтверждено, оставь `null` и укажи причину в реестре исследования. Не копируй общие геометрические значения `specs` в канал без подтверждения, что они относятся именно к нему. Для обычной одноканальной камеры массив `channels` не добавляй.

## Создание нового JSON

- создай итоговый JSON с нуля по структуре объекта из этого промпта;
- включи все IP-камеры из переданного прайса и только их;
- перенеси цену, валюту, код и ссылку на карточку из соответствующей строки прайса;
- не добавляй аналоговые камеры, аксессуары и позиции, тип которых не удалось подтвердить;
- не создавай дубли одной позиции: сверяй код, бренд, модель и модификацию внутри прайса;
- для каждой характеристики сохрани источник и статус подтверждения в соответствующих полях объекта;
- для многоканальных моделей сохрани подтверждённые параметры каждого видеоканала в `channels[]`;
- если структуры примера недостаточно для источников отдельных характеристик, опиши требуемое расширение и покажи пример объекта с ним в отчёте.

Проверь, что JSON синтаксически корректен, а типы значений соответствуют схеме проекта.

## Обязательная проверка полноты

В конце сравни количество строк категории «Камеры» в прайсе с итоговым реестром. Для каждой позиции должна быть ровно одна категория решения:

- IP-камера, обновлена/добавлена;
- не IP-камера, пропущена с причиной;
- не удалось определить, требует ручной проверки.

Никакая позиция не должна исчезнуть из отчёта.

Также выведи пересекающиеся счётчики неполных данных:

- ни у одного канала/геометрического набора камеры нет горизонтального разрешения;
- ни у одного канала/геометрического набора камеры нет распознаваемого оптического формата сенсора;
- ни у одного канала/геометрического набора камеры нет диапазона фокусного расстояния;
- количество уникальных камер, у которых ни один отдельный канал/геометрический набор не содержит все обязательные поля.

Для одноканальной камеры геометрический набор — это соответствующие поля в `specs`; для многоканальной — каждый отдельный объект в `channels[]`. Не объединяй отсутствующие поля разных каналов в один набор и не считай модель неполной по общим `specs`, если хотя бы один её канал содержит все обязательные поля.

Укажи, что эти числа пересекаются и не складываются.

Посчитай пропуски непосредственно по итоговому JSON, отдельно для каждого поля и для уникальных записей. Не копируй счётчики из предварительного отчёта. Повтори расчёт вторым независимым проходом и сравни результаты. Если несколько счётчиков совпали, проверь записи по кодам: совпадение допустимо только если у них действительно одинаковый набор пропусков.

Для каждой IP-камеры итоговый JSON должен содержать либо подтверждённое значение, либо `null` для каждого поля из образца. Для каждого `null` в рабочем реестре должна быть причина: официальный источник не публикует параметр, точная модификация не установлена, страница/документ недоступны после нескольких попыток либо источники противоречат друг другу. Не ставь один общий статус «не проверено» всем моделям, которые не успел исследовать.

## Критерии приёмки — обязательны для финального ответа

Финальный ответ можно отправить только после выполнения всех пунктов:

1. Число строк в реестре равно числу строк категории «Камеры» в прайсе; каждая строка учтена ровно один раз.
2. Каждая строка имеет обоснованную классификацию: IP-камера, не IP-камера или неразрешённый спор с конкретной причиной и результатами поиска.
3. Новый JSON сформирован целиком и содержит все подтверждённые IP-камеры из прайса, а не только модели, для которых характеристики нашлись быстро.
4. Для каждой модели проведён поиск источников по характеристикам. Модель без найденных характеристик всё равно должна иметь запись в итоговом JSON и отдельную строку в реестре исследования с перечислением проверенных источников и причин оставшихся `null`.
5. Итоговые счётчики пропусков пересчитаны непосредственно из JSON и согласуются со списком кодов моделей, у которых есть пропуски.
6. Созданы и приложены как отдельные файлы: итоговый JSON, полный реестр строк прайса, реестр исследования характеристик и список нерешённых случаев.
7. JSON разобран валидатором; количество объектов и ключевые поля проверены автоматическим скриптом или эквивалентной проверкой.

Если лимит времени или сообщения мешает завершить работу за один проход, продолжай следующими пакетами и сохраняй промежуточные файлы. Не выдавай их за финальный результат, пока все критерии приёмки не выполнены. Если внешние сайты недоступны, продолжай по доступным официальным документам и явно укажи только конкретные оставшиеся блокеры, не называя весь каталог завершённым.

## Результат

Подготовь:

1. итоговый JSON-каталог;
